# TSP_Cam — Technical Risk Audit (2026-10-08)

This audit checks design assumptions against official Raspberry Pi/BlueZ/Microsoft documentation and reported Picamera2 failures. **No physical PiCam has yet been benchmarked; reported risks are hypotheses or upstream issues, not proven bugs in TSP_Cam.** Priorities: P0 blocks recorder launch; P1 blocks technician pilot; P2 can wait.

## Executive findings
1. **P0 — 1080p crop and traffic-counting FOV.** OV5647 native 1920×1080 captures a central region (roughly 1928×1080 from 2592×1944 full sensor); 1296×972 is a full-FOV binned mode. 1080p could cut traffic arms out of view! Add a 1280×960@30 4:3 profile, derived from full-FOV mode if confirmed. Compare side-by-side capture from fixed tripod at 800×600 / 1280×960 / 720p / 1080p. Choose production default based on usable junction coverage and OCR, not only pixels. Source: https://github.com/raspberrypi/libcamera/issues/225
2. **P0 — Silent capture stalls despite live processes.** Reports include Zero 2 W video/request stalls and 11–13h stalls on other Pi hardware. Watchdog must check **fresh frame metadata and encoded output timestamp, byte progression, timed segment close**. A single liveness check is insufficient. Service restart with bounded backoff; explicit incident/gap record. Test >48h, including reboot and stalled capture injection. Sources: https://github.com/raspberrypi/picamera2/issues/1404 , https://github.com/raspberrypi/picamera2/issues/1392
3. **P0 — Buffer lifetime and preview interference.** Pi Zero 2 W users report slow MJPEG and possible camera buffer exhaustion when requests aren't released. All Picamera2 requests must be released promptly. Preview should drop stale frames, cap queue to one, throttle JPEG rate 1–2fps, stop on timeout and have lower priority than recording; verify no recording gaps with multiple browser requests. Source: https://github.com/raspberrypi/picamera2/issues/1085
4. **P0 — Trixie not yet qualified.** Specific issue #1358 reports a sensor_modes memory allocation failure with Trixie on Pi Zero 2 W but not on Bookworm in reporter's setup (reported camera sensor is different). Do not treat Trixie as mandatory production baseline. A/B test current **Bookworm Lite 32-bit vs Trixie Lite 32-bit** with OV5647 and selected Picamera2/library stack, then pin known-good image/dependencies. Source: https://github.com/raspberrypi/picamera2/issues/1358
5. **P0 — Loss of USB power and non-journaled exFAT.** Throughput at 5–10Mbps is trivially below USB 2.0 capacity but mount loss, brownout, write caching, sudden cutoff and FAT/exFAT damage matter. Microsoft explicitly documents that exFAT has **no metadata journaling**. Record mount source identity and free space; wait for USB and fail loudly, never write into an empty mountpoint directory on microSD; test fsync, unplug, dirty media, fsck and corrupted segment recovery. Benchmark exFAT (office compatibility) vs ext4 (journaled; Windows extra workflow). Sources: https://learn.microsoft.com/windows/win32/fileio/filesystem-functionality-comparison ; https://www.raspberrypi.com/products/raspberry-pi-zero-2-w/
6. **P0 — Recording continuity vs MP4 file finalization.** A normal MP4 may become unplayable on unclean shutdown when metadata is not finalized. A raw H.264 bitstream is more recoverable but has poor Windows/browser compatibility and no reliable per-frame presentation timestamps. Compare native `PyavOutput`/fragmented MP4, transport-stream segments and H264+PTS sidecar; verify Windows/TSP AI reads. New Picamera2 example `SplittableOutput(PyavOutput(...))` shows switching files at I-frames without missed frames; evaluate on pinned library version. Source: https://github.com/raspberrypi/picamera2/blob/main/examples/split_output.py ; https://www.raspberrypi.com/documentation/computers/camera_software.html
7. **P0 — In-frame timestamp correctness, not just pretty text.** Drawn on every frame despite only updating glyphs once a second. Danger: callback stalls capture, local clock steps backward/forward, DST ambiguity, drift or invalid RTC yields misleading timestamps. Map capture sensor monotonic frame timestamp to corrected UTC; overlay date/time in contract timezone with explicit DST handling; log clock step/time authority and OCR verification. Benchmark low ROI CPU compositing at 800x600/1280x960/1080p. Source: https://github.com/raspberrypi/picamera2/blob/main/examples/timestamped_video.py
8. **P0 — 512MB RAM, low voltage, thermal pressure.** Never count only CPU load; monitor RSS, CMA/buffers, OOM, temperature, `vcgencmd get_throttled`, USB disconnect logs, frame-to-frame delays. Avoid desktop and background apt upgrades, OpenCV processing on full frame, unbounded queues and multi-encoder setups. Check actual power supply under load in enclosed camera box. Source: https://www.raspberrypi.com/documentation/raspbian/README.md
9. **P1 — Bluetooth PAN: capability is not a complete UX.** BlueZ supports PAN but real Android pairing, tethering, DNS/IP discovery, mobile browser reaching Pi, and re-connection after screen sleep must all be tested on actual Android handset/OS. Provide tested URL/pairing flow, no expectation that browser magically discovers `bnep0`. Source: https://bluez.readthedocs.io/en/latest/network-api/ ; https://raspberrypi.stackexchange.com/questions/108120/host-web-server-on-raspberry-pi-via-bluetooth-pan
10. **P1 — 15-minute Wi-Fi AP startup is not sufficient emergency recovery.** If Bluetooth fails at hour 3, no AP remains. Add controlled **physical re-enable** (button/reed switch/test-point action) or alternate safe non-destructive service boot; avoid forced reboot of a recording camera merely for maintenance. Make AP timer monotonic and fail-closed, per-device password, auth on panel, expiring pairing.
11. **P1 — Remount/format footgun.** `/dev/sda` is not stable USB identity; USB mountpoint may exist on microSD when media absent. Use blkid/udev mount source checks, safe device selection, deny root/boot device and mount namespace overlap; two-stage operator confirmation. Persist format audit outside target media *before* start and after result. Never format an active capture volume until stopped/closed.
12. **P1 — Logs on SD vs read-only root contradiction.** An overlayfs read-only root improves resilience but loses writes on reboot. Updater and durable SQLite state require a separately writable persistent partition. Phase 1 chooses a modest writable ext4 OS plus bounded/fsynced event journal and backups; optionally explore read-only root + separate small `/var/lib/tspcam` state partition in Phase 2. Avoid assuming overlayfs is free improvement. Source: https://www.raspberrypi.com/documentation/computers/configuration.html ; https://pip-assets.raspberrypi.com/categories/685-whitepapers-app-notes/documents/RP-003610-WP/Making-a-more-resilient-file-system
13. **P1 — Updating the app is not updating the OS.** A/B app rollback cannot repair a bad SD, libcamera ABI mismatch, corrupt filesystem, driver/firmware updates, or interrupted package-manager operation. Freeze tested dependencies; handle security updates in controlled re-imaging/maintenance workflow. Persist independent last-good transaction and test reboot from interrupted activation. Source: https://github.com/raspberrypi/picamera2/issues/1362
14. **P1 — Private GitHub update credentials at fleet scale.** Unauthenticated `raw.githubusercontent.com` one-liner fails on private repo. Do not place a permanent GitHub read/write token on hundreds of units. Prefer signed versioned release tarballs through authenticated TSP OS mirror with short-lived read-only access; pinned signing verification key; update panel not root.
15. **P1 — Recorder integrity vs download/file browser.** Browser video players do not natively support bare H.264 files reliably; previewing/downloading many gigabytes over Bluetooth competes with capture. Serve metadata and capped previews; stream/copy only closed validated files. File listing paginated and read-limited; do not derive trust from filename paths.
16. **P1 — Power loss is a field-design problem, not solely software.** No app can flush media when 5V suddenly disappears. Add controlled low-power shutdown/hardware reserve on battery revision. For now test worst-case repeated surprise power drops on mains and various USB sticks; avoid promises of zero loss.
17. **P2 — API/privacy controls.** Field videos can contain identifiable road users: require strong unique per-device credentials, authenticated routes, CSRF protection on destructive actions, least privilege for services, and explicit sync scope. AP open merely to display 'service' is not authorization.
18. **P2 — Camera autodetection does not guarantee lens actuation.** OV5647 sensor ID is not proof of focus/zoom motor or driver. Build capabilities from libcamera controls and validated model adapters; don't expose inert UI controls.
19. **P2 — Storage estimator must use measured bitrate.** Nominal 5Mbps H.264 is not guaranteed file size; include container overhead, reserve space, observed rolling throughput and correct GB/GiB reporting.
20. **P2 — Technician intervention/operational gap accounting.** Restarts, mode changes, update windows and service format all can create video gaps. Define record-oriented gap ledger and a one-tap exportable site installation report. No silent restarts or gaps.

## Corrected implementation choices
- **Do not default to 1080p until field-of-view / sustained benchmarks pass.** Evaluate 1280×960@30 first for 4:3 traffic survey coverage.
- **Do not require Trixie from day one.** Trixie and Bookworm are pilot candidates; select and pin based on same unit tests.
- **Prefer in-process Picamera2 H264 + SplittableOutput for overlay/preview if performant.** Keep bare `rpicam-vid` as diagnostic baseline / fallback.
- **Approved operation: physically split MP4 files on full local clock-hour boundaries, with a shorter first file.** Earlier proposals to use shorter resilient internal segments or logical hourly groups remain unapproved research alternatives, requiring explicit operator decision; preserve files for TSP MP4-fix repair and test sudden power loss.
- **Hardware recovery AP after the initial 15 min is a real requirement** if the Bluetooth link is considered primary.
- **Track actual capture gaps**, with event timestamp accuracy and test fixture playback, not solely 'recording' green state.
- **Maintain production write targets outside the application versions** and avoid blindly mounting arbitrary USB as official recordings drive.

## Mandatory acceptance matrix
- Single fixed junction scene / lens; compare real FOV & quality across all 4 profiles.
- >48h video/no overlay; >48h overlay + 2fps preview; compare frames, bitrates, resource usage, sample footage and gaps.
- Low voltage, USB disconnect, FS read-only, mounting non-existent USB, disk-full, bad RTC, invalid time and power-cut at minute 59.
- Browser open/close 100x, concurrent status checks, file browsing under recording, multiple clients and abrupt BT/Wi-Fi loss.
- 15-minute AP off test; physical AP recovery at 3h; pairing with current Android OS; service without Wi-Fi access.
- Security: wrong-device formatting blocked, no unauthenticated format/reboot/update, malicious path blocked, signature mismatch update rejected.
- OTA: new version fails to start or stalls recording; revert to signed last-known-good; verify unchanged USB data.
- Loss budget (recording gaps, FPS minimum, corrupt segment maximum, mAh/h, CPU/RAM) defined from baseline and signed off before field rollout.
